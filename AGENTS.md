Margarine intentionally continues compilation after diagnostics. The presence of compiler errors is not a fatal condition and must never, by itself, prevent code generation. Do not add early exits, aborts, or guards based solely on emitted diagnostics.
Do not stop at a merely adequate solution. Actively look for remaining correctness issues, edge cases, unnecessary complexity, and opportunities to produce a cleaner or more complete result before declaring the task finished.

# Repository Test Policy

You MUST run the complete, unfiltered core language suite from the repository root after every change to any project or repository file:

```sh
cargo run -p margarine -- test tests/core.mar
```

Do not replace this check with a filtered test invocation. A change is not verified until the full suite has run; report every failing test and its failure output. Existing baseline failures must be compared against a clean checkout before attributing them to the change.

The `margarine check` CLI command runs tokenization, parsing, and semantic analysis only: it reports diagnostics and exits non-zero when any error was reported, without emitting code, linking, or invoking codegen. Codegen remains unconditional after diagnostics for `build`, `run`, and `test`; `check` deliberately does not run it. `cli/compile.rs::check` drives the public `Compiler` + `CompilationResult` API directly and counts the nested diagnostic reports returned by `Compiler::check`.

The CLI is organized under `margarine/src/cli/`: `mod.rs` owns the clap-derived `Cli`/`Commands` surface (`check`, `build`, `run`, `test`, `clean`, `update`, `install`, `toolchain`), dispatch, typed `CliError`, and exit-code rendering; `compile.rs`, `test.rs`, and `artifacts.rs` own compiler execution, the test runner, and cache lifecycle respectively; `distribution.rs` owns shared release/download/checksum/extraction mechanics used by the policy-specific `install.rs` (self-install of an unmanaged binary), `update.rs`, and `toolchain.rs`. `margarine/src/main.rs` is only the process boundary and the sole `std::process::exit` callsite. `toolchain add <target>` requests the release matching the installed compiler version, downloads `margarine-toolchain-<target>.tar.gz` plus `.sha256`, verifies the checksum, safely extracts it into a same-filesystem staging directory, requires at least one regular file under `libs/`, and atomically renames the staging directory to the versioned toolchain path; unlike artifact-touching compilation commands, it does not acquire `artifacts.lock`. Add subcommands in `cli/mod.rs`, not through hand-rolled `std::env::args` parsing. `--target` and `toolchain add` targets parse through `CompilationTarget: FromStr`, so new targets need both a `TryFrom<&str>` arm and a `FromStr`-visible variant.
`mar install` turns an unmanaged executable into a managed installation: it refuses when `current_installation()` already resolves (the running binary is managed), requires `HOME`, acquires the same `Installation` transaction as `mar update`, stages the current executable plus the host toolchain from the release matching its own `VERSION`, activates the stable symlink, and prints PATH guidance when `<root>/bin` is not on `PATH`. It shares `checked_toolchain_assets` with `toolchain add` so a release missing host toolchain assets fails before any prompt or download. The shared transaction lives in `cli/installation.rs::Installation::install_release`: validate release tag ↔ requested version, reject an existing destination, stage under `.staging-*` inside the root, verify the staged binary's `--version`, install toolchains, re-check the destination, atomically rename, re-check that the active symlink target did not change concurrently, swap the symlink, run a final binary check, and roll back link + delete the new version on failure (keeping the new version only when rollback itself fails). `installation_from_executable` additionally validates the version directory name is exactly three numeric components.
`mar install` is always explicit: bare `mar` prints help and must not contact the network, create installation state, or prompt to install. Ordinary compiler commands (`check`, `build`, `run`, `test`, `clean`) work from unmanaged/source-built binaries; only self-management operations that need a managed layout (`update`, `toolchain add`) require one.
`mar update` holds an exclusive kernel lock on `<installation-root>/update.lock` before contacting the release API and through activation, serializing concurrent updater processes before any asset download. The destination is still checked both before prompting/downloading and immediately before publication so unrelated filesystem changes cannot be overwritten.
Source-level external file/resource declarations such as `extern "path";` and `@hash` are unsupported and are not downloaded, hashed, cached, or passed to linkers; `extern { ... }` remains the function-ABI declaration form. Imported packages produce link inputs only through their `build.mar` scripts, which compile in an isolated in-process workspace before execution.
Standard `core` and `std` packages ship target-specific runtime archives under `lib/<target>/`; the Margarine installer places them into `~/.margarine/<compiler-version>/toolchains/<target>/libs/` (overridden by `MARGARINE_TOOLCHAIN_DIR`). Every native and Wasm link invokes the target-specific `libs/` directory as a linker search path and dynamically passes every regular file in that directory as an explicit link input. Those bootstrap packages do not use generated `build.mar`; ordinary imported packages still use `build.mar` for link inputs.
In unmanaged debug builds from this checkout, the compiler uses `../libraries` as the default `pkg:` source and prelude source. Runtime archives come from the normal compiler-versioned toolchain under `~/.margarine` (or `MARGARINE_TOOLCHAIN_DIR`); rebuild `core/native/lib.c` and `std/native/lib.c` and copy the target archives there when those sources change. No compiler build script compiles runtime libraries. `MARGARINE_LIBRARY_DIR` can override the source package root.
The native Linux targets are `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`; native executable linking uses `clang` with `libstdc++`, while test libraries use `.so`. Native non-Wasm external ABIs use indirect returns for structs larger than 16 bytes on every supported native target.
Help styling uses the project's `colourful` crate (never another colour crate); codes are gated automatically by `NO_COLOR`/TTY detection, and clap's writer strips ANSI on non-TTY output, so piped help stays plain.
Path arguments are validated at parse time through clap `value_parser` functions (`existing_path`, `existing_file_path` in `cli/mod.rs`) instead of panicking inside compilation: source inputs to `build`/`run` must be existing files, and `test`'s path must exist (default `.`).
The whole CLI status fleet is `indicatif`-native and centralized in `margarine/src/progress.rs`: every new command must express indefinite work through `StatusLine` and determinate byte/item work through `byte_progress`/`item_progress`, rather than inventing command-local presentation. Determinate work starts with the shared green spinner and expands to the shared 40-column cyan/blue `█▓░` bar on the first non-zero progress update at or after 100 ms; fast operations therefore never flash a full progress bar. All status/progress draw targets are selected centrally and hidden on non-TTY streams. `StatusLine` always owns a lifecycle object, even when hidden, so callers suspend, finish, or clear it directly without optional-status branches.
Covered emitters: stable compiling bar (`start_compilation_status` in the build/test/check orchestration), `Linking|Linking browser Wasm` (`link_compilation`, no depth parameter), `Running build script` (`run_build_script`, cleared rather than settled because the script's own output follows), `Cloning` → `Cloned <url>` (`load_repository`), test-dylib linking (`run_step` in `cli/test.rs`), per-test execution (`run_tests`, with each result printed while the shared `Testing <name>` item bar is suspended), and updater check/download/extract/verify work. Nested in-process compilation and build scripts borrow the existing thread-local compile bar; messages are restored on success, failure, early return, and drop. Independent threads own independent bars.
`clean` removes the cache directory through `clean()` in `cli/artifacts.rs`, which drives the shared `item_progress` bar (`Removing <size> <bar> n/total (eta)`, hidden when piped) and ends with a `✓ Removed N files, <size>` summary; per-file removal failures suspend the live bar before printing warnings and produce the partial-failure summary instead of claiming success. Cache traversal and byte accounting use symlink-aware metadata: nested symlinks are unlinked without following them, and a root cache path that is a symlink or regular file is removed as one file rather than traversed as a directory. Byte sizes render through `format_bytes` (b/KiB/MiB/GiB).
Prelude/repo caches under the cache directory are self-healing: when an `ImportRepo` cache entry exists but is not a valid git repository (e.g. leftovers from an interrupted build or a partial clean), the compiler removes it and re-clones instead of recording `RepoDoesntExist` and skipping the module — a gutted cache must never poison linking with missing runtime symbols. `clean` reports per-file removal failures as warnings and prints a partial-failure summary rather than claiming success.
Cache resets are a flag, not a command: `check`, `build`, `run`, and `test` accept `--update` (cache reset), which is distinct from the `mar update` release-check subcommand; pure cache deletion is `clean`.
`mar update` is a fully manual release check and installer — no background spawns, no notices on other commands. It requests `latest` from the release API (`MARGARINE_RELEASES_API` overrides the API base URL for tests/mirrors), compares `tag_name` against the managed active version directory as exactly three numeric components (never string compare, and malformed versions are rejected), and renders a git-style dialogue: 404 means "no releases yet" + exit 0; up-to-date prints a check line + exit 0; a newer version pages the notes through `$MARGARINE_PAGER`/`$PAGER`/`less` only when stdout is a TTY and content exceeds terminal rows (TIOCGWINSZ), then shows an `[y/N]` prompt whose yes-branch runs the self-update pipeline. Other HTTP and network failures exit 3 (`LINK_ERROR`). The same API base serves exact installed-version lookups at `tags/v<version>` for `toolchain add`, including calls made by a staged updater binary; no release metadata is persisted or passed through the process environment.
The updater treats the version directory containing the active executable as authoritative for installation and toolchain paths; a staged binary's reported `--version` output is only required to be nonempty and is not required to match the release tag. Before showing the release dialogue or downloading assets, it rejects an existing destination version and validates the host and carried-toolchain asset/checksum pairs and their HTTP(S) URLs. Downloads fetch and validate the checksum file before transferring its archive.
`mar update` installs only the versioned layout `~/.margarine/<version>/bin/margarine`, activated through the stable relative symlink `~/.margarine/bin/margarine`; legacy single-binary layouts are rejected. Its fixed pipeline selects the release-scoped asset `margarine-<host>.tar.gz` plus `.sha256`, verifies the checksum, safely extracts every archive entry under the staged version's `bin/`, and requires a regular root `margarine` entry whose staged `--version` succeeds with nonempty output. Archive paths must be relative, duplicate file destinations and non-file/non-directory entries are rejected, and existing files are never overwritten. The host and every supported directory under the active version's `toolchains/` are expected as `margarine-toolchain-<target>.tar.gz` plus `.sha256`; missing assets require an explicit per-target confirmation, and accepted omissions are not carried forward. Available toolchains are installed into the staged version before one atomic directory rename publishes it; activation atomically replaces the stable symlink, verifies through that final path, rolls the link back on failure, and deletes the failed version only when rollback is confirmed.
An executable outside the managed `<version>/bin/margarine` layout cannot safely derive an installation root or rollback target and is rejected as not managed by the self-updater; the diagnostic shows the executable path and directs the user to the original installation method instead of exposing directory-shape validation details.
Byte-counted work (download, hashing) renders progress through the `byte_progress`/`ProgressReader` pair in `margarine/src/progress.rs`: construct with `byte_progress(Option<u64>)` (`None` only when the byte count is unknown), feed via `ProgressReader`'s `Read` implementation, and clear with `finish()`. Item-counted work uses `item_progress`; both use the shared determinate visual grammar. Item progress advances only on caller updates and deliberately has no background ticker thread, because the native test runner forks while its item bar is live. `StatusLine` completion switches from the spinner template to a message-only template so the `✓` occupies the spinner's column and completed text aligns with active text. `ProgressReader` increments only after successful reads and counts exactly the bytes returned.
Every cache-touching command (`build`, `run`, `test`, `check`, `clean`) accepts `--cache <dir>` (default `artifacts`). Derived paths must always be computed from the cache parameter — the test dylib is `<cache>/program.dylib`, and `run` executes via the absolute-ish path returned by `compile_and_link` rather than prefixing `./`, which breaks for nested custom cache dirs. `run` reports its source path rather than its generated executable path.
All artifact-touching commands (`check`, `build`, `run`, `test`, `clean`) hold an exclusive `flock` (via the `fs2` crate) on `artifacts.lock` at the project root for their whole run. The lock file must stay outside the cache directory: deleting a held lock file leaves latecomers locking a fresh inode with no mutual exclusion. Contention displays a transient `waiting for artifacts lock` `StatusLine` spinner, hidden on non-TTY stderr and cleared immediately after acquisition; kernel release on process death makes stale locks impossible.
Package sources and generated artifacts have separate cache roles. Downloaded repositories live once at `<cache>/repos/<hash>/`; nested build-script compilations reuse that repository cache rather than cloning packages into their isolated compiler cache. Each compilation creates a clean `<cache>/build/<hash>/` containing the writable `package/` materialization, `out/` (`MARGARINE_OUT_DIR`), `cache/` for the isolated nested compilation's intermediates, and the directly contained `build-script` executable plus its compiler intermediates. When an imported package contains a direct `build.mar`, `margarine/src/lib.rs` compiles it through the reusable compiler/linker pipeline in that hash directory, then runs the generated executable from `package/`. The build script receives `MARGARINE_BUILD_SCRIPT=1`, the parent's prelude list, `MARGARINE_COMPILATION_TARGET`, `MARGARINE_PACKAGE_DIR`, `MARGARINE_OUT_DIR`, and a nested `MARGARINE_BUILD_DEPTH`; successful stdout is consumed for `margarine:link=...` directives. Its nested in-process compilation reuses the thread's live compilation bar and emits no progress when stderr is not a TTY. The build script itself compiles for the host target so it can execute; launch, compile, and non-zero-exit failures propagate as typed `CompilerError` values and CLI callers report them as `LINK_ERROR`, never as a panic. Package materialization copy failures also propagate as typed `CompilerError` values rather than panicking. Build-script compilation and execution consume the same captured process environment with Margarine metadata overrides, so cfg evaluation and runtime lookup cannot drift.
`MARGARINE_OUT_DIR` is deliberately `../out`, relative to the build script's `package/` working directory, so shell-based tools can consume it without breaking on spaces in the project path. Build scripts should write generated files below that directory and emit the same relative path in `margarine:link=...`; link directives remain resolved from `package/`.
Exit code contract: 0 success; 1 compilation errors or failing test suite (`COMPILE_ERROR`); 2 CLI misuse (clap owns it); 3 link/toolchain failure (`LINK_ERROR`); `run` propagates the child program's own exit code when it is in the portable 0..=125 range, else 4. Command implementations return `CliResult` instead of terminating the process; `cli::main` renders `CliError` once as a clap-styled `error:` message with no usage or help suffix and returns its status, and `margarine/src/main.rs` performs the sole process exit. Error counts over the `[Vec<Vec<String>>; 3]` check result must flatten twice: the outer array holds per-stage vectors of per-file vectors, so `errors.iter().flatten().map(|f| f.len())` counts reports while a single `.iter()` accidentally counts files.
Compilation is driven through the `Compiler` + `CompilationResult` API (`margarine/src/lib.rs`): construct a `Compiler`, register the entry via `FileData::open` + `files.register`, then `compiler.run(&settings) -> CompilationResult`, `compiler.check(&mut result)` (prints diagnostics, returns `[Vec<Vec<String>>; 3]`), and `compiler.codegen(&settings, &mut result, errors)`. The old free-function wrappers `margarine::run`/`margarine::check` are removed; test names come from `result.tests()` (symbol ids + `should_panic`, resolve names through `compiler.string_map`).
`build` and `run` share `compile_and_link()` in `cli/compile.rs`, which delegates the reusable `margarine::build` compiler/linker pipeline; `run` executes the absolute output path returned by that pipeline.

Language declaration policy: `type` declarations are aliases only (`type Name = Type;`). Standalone opaque declarations (`type Name;`) are not supported.
Testing policy: prefer in-language `.mar` tests under `tests/` for observable language and compiler behavior whenever the behavior can be exercised through the language test runner. Do not duplicate that coverage in Rust tests. Keep Rust-side tests for parser/AST contracts, low-level implementation contracts, and diagnostics or compile-failure cases that cannot run in-language.

Alias validation errors, including recursive aliases and invalid alias definitions, must be reported at the alias definition rather than at a later use site.
The field-doesn't-exist diagnostic may suggest importing implemented traits that provide the missing method; suggestion candidates come only from the receiver type's own trait-impl map (generic bounds, `ns == NamespaceId::MAX`, are excluded), gated by `type_implements_trait` — never from a program-wide scan — and the struct-literal field check never receives suggestions. Suggested traits render with their full defining-namespace path (`ns path :: name`) because trait symbols, unlike containers, store only their plain local name.
Alias-qualified namespace expressions resolve generic parameters uniformly through the canonical type path; generic arguments must remain available to member analysis rather than being selected by an alias-specific branch. Qualified type conversion preserves the original requester scope so private members cannot be accessed through a namespace fence.

Formatting policy: NEVER run `cargo fmt`. Preserve and maintain the existing project styles and formatting conventions when editing files. For multi-line right-hand-side expressions, put the binding or operator on its own line and start the expression on the next line: write `let value =` followed by `if`, `match`, or a multi-line function expression/call. Apply the same layout consistently to nested expressions. For `if let` chains, keep each `if let ... = ...` binding on one line when it fits; break before the chained `&&` condition rather than after `=`.
Semantic error IDs and error nodes remain one-to-one; propagated parser/lexer errors and already-registered semantic errors update type information without appending duplicate nodes. Error-producing semantic helpers bind each error to its originating `NodeId`; no error-node backfill is used. Every analyzed expression receives `ExprInfo { ty }` — an errored expression carries a per-failure error type, so `Type::ERROR` and `ExprInfo::Errored` no longer exist. Failed type resolutions register a fresh per-failure symbol whose kind is `SymbolKind::Error(ErrorId)` (each failure its own symbolmap entry via `SymbolMap::error_sym`; no shared error sentinel exists — `SymbolId::ERROR` and `Type::ERROR` are gone, so an errored value is always a per-failure symbol carrying its originating id); the errored field/argument `Generic` records that symbol through the ordinary `GenericKind::Sym` kind. Type resolution is infallible: `Generic::to_ty`, `dt_to_gen`/`dt_to_gen_ex`/`dt_to_ty`/`dt_to_sym`, and `convert_symbol_get_result` return the value directly and materialize error types/symbols (via `error_type`/`error_generic`/`error_sym`) instead of returning `Result`; `Type::sym` keeps its `Result` because a `Type::Var` has no symbol, `resolve_generics` keeps its `Result` because it validates declarations rather than resolving a type, and codegen's `Result<(Value, Type), ErrorId>` is control flow (bypass propagation), not resolution. `Type::is_err`/`err_id` and type-equality taint are kind-based (`is_err_sym`, tolerant of two-pass pending entries via `sym_ok`), catching sentinel and per-failure symbols alike, so a field recorded with an error type taints every comparison it participates in and error-typed expressions propagate their originating id. Struct literals with error-typed fields are poisoned by typing them as the first errored field; codegen runs after semantic errors, treats error-typed expressions as their recorded error id (every error path carries a real registered id; `ErrorId::Bypass` is gone) rather than panicking. Calls to trait-validation-broken methods fail fast because `get_func` consults the callee's recorded decl error (set by the trait-impl signature validation via `self.error(decl, …)`); the old per-symbol `err` field is gone. Codegen dispatches on `SymbolKind::Error` in `to_llvm_ty`, `create_struct`, `create_enum`, `resolve_pattern`, and the enum-constructor path instead of assuming containers. Namespace resolution keeps its own `SymbolGetResult::Errored` channel: two-pass decl processing maps a failed name to a hard error entry so pass 2 can bail before `add_sym`, which an error symbol could not do. If qualified namespace resolution yields `SymbolId::ERROR`, semantic analysis must not recurse into the action; it records the existing alias error on the namespace expression so codegen skips the unanalyzed action.

Resolution and decl/use codepaths do not re-check for error symbols after `convert_symbol_get_result` — `error_sym_of`/`gen_is_error` no longer exist. Resolution continues with the id, and the impl and use machinery runs on error symbols too: impl bodies are collected into the error symbol's namespace and analyzed, and cascading lookups (e.g. `use a::b` with `a` missing) emit further diagnostics. The `GenericLenMismatch` checks in `dt_to_gen_ex`/`dt_to_ty` are skipped when the resolved base is an error symbol, because its placeholder generic count (0) is meaningless; `dt_to_ty`'s generics buffer is sized to the argument list, not the declared count. `Type::is_err` and `Type::err_id` are recursive: a type containing an error-typed generic argument counts as error-typed (`[Missing]` is an error type), and `err_id` returns the first contained error so codegen's `out_if_err!` skips such values and the runtime panic carries the real message. Classification checks pass for error-typed values: `Type::is_int`/`is_float`/`is_num` short-circuit on `is_err`, and the binop/unary arms check the recursive `is_err` before their `supports_*`/operator checks, so error operands flow through range, index, shift, cast, and operator checks and propagate instead of emitting secondary diagnostics. When a variable hint is error-typed, the initializer is still unified with the hint before the early return so its inference vars resolve. The two-pass boundary: names are pre-registered as pending entries (`self.syms[i].0 == Err(gen_count)`) and finalized by `add_sym` in `compute_types`; resolution during `collect_impls`/`collect_uses` legitimately sees pending ids (stable, content arrives later) and must only use the tolerant accessors — `is_err_sym` (`Err(_) => false`), `sym_ok` (`Option`), `sym_gens_size` (`Err(v) => v`), `sym_ns` — never the strict `sym()`, which unwraps and is reserved for finalized contexts (node walk, codegen). Error symbols are always fresh entries; a pending entry can never become an error symbol, so treating pending as "not an error" is by construction.

Codegen struct construction materializes every declared field; an omitted field is valid only when its type is error-typed and is represented by a zero value of the concrete, zero-field `{error}` LLVM type. Missing non-error fields remain semantic errors.
Extern calls and function materialization recursively reject error-typed arguments and returns by propagating the originating error; codegen must not materialize an external ABI containing `{error}`.
Match codegen pattern bindings are stack-scoped and must be popped even when branch expression codegen returns an error; diagnostic codegen must not leave nested bindings to corrupt enclosing switch cleanup.
Enum constructors receive the selected payload type; only that variant is zero-filled when its payload is error-typed, so valid variants in an enum with another errored payload preserve their values. Enum accessors propagate error-typed payloads before LLVM loads.
LLVM builder field stores take an explicit field index and accept typed values through `Deref<Target=Value>`. Builder locals use owned stack slots; closure captures are copied into invocation-local slots and are immutable at the semantic layer.
`Builder::ite` handles ordinary conditionals with builder-only closures; `Builder::ite_ex` exposes mutable state for stateful branches. `Builder::iff` wraps `Builder::ite` for an else-less branch and preserves the existing three-block lowering.
No-capture closures bypass heap environment allocation and `__closure_drop` synthesis, instantiating `funcRef` with a null environment pointer so copies and drops remain zero-overhead no-ops.

Collection iterator codegen uses a fixed inline pending-range frame array rooted by one collection value. Frames store tagged collection pointers plus half-open unsigned i64 ranges and are reused by stack slots rather than allocated per element. Native ListIterNext inout arguments use the ordinary temporary aggregate writeback path.

ListIter<T> is an opaque inline stack value. `to_llvm_ty` maps it to the inline `collectionIter` aggregate; copies use ordinary aggregate value semantics with independent cursor state, while the aggregate's first collection field delegates ownership to the existing `List<T>` copy/drop semantics. ListIter itself has no refcount or shared cursor state. Closure captures are immutable inside closure bodies; capture values remain owned by the closure environment and are copied into invocation-local slots for reads.

By-value parameters are owned copies: the caller keeps its own reference (a call-site copy is made for variable arguments and released after the call), and the callee clones every non-inout parameter at function entry and releases it at exit (registered as ordinary droppable locals). Owning from entry keeps every intra-body drop — assignment overwrites and exit cleanup — targeting an owned value; the clone/drop pair is local to the callee so LLVM can fold it when the body never touches the refcount word. Inout parameters and closure captures remain borrowed (writeback slots and closure-env-owned respectively).

`let` bindings are immutable; `var` bindings are mutable. `VariableScope` carries the `mutable` flag and identifier analysis maps it to `ExprInfo::is_mut`, so `UpdateValue` and inout-argument checks reject immutable bindings, including field/index access through them. Function parameters, for-loop bindings, match bindings, and closure parameters remain mutable; closure captures stay immutable via `AnalysisResult::captured`.

Collection metadata stores the logical length in the low 59 bits of an i64 word and the rope depth in the high 5 bits; allocation-size conversions remain checked and target-`usize`-bounded.


Rope concat and slice operations materialize collections deeper than 16 levels into flat storage; recursive flattening copies borrowed ranges and releases the consumed roots.
Native library functions that consume strings receive `Ptr<byte>` and an explicit length; compiler codegen does not emit a string-copy helper for native calls.
Compiler intrinsic `$float_sqrt` is language-visible as `float -> float` and lowers to LLVM `llvm.sqrt` without a native library dependency; observable coverage belongs in `tests/core/`.
The compiler wraps the entry file in a synthetic root module named after the source file stem (`testmar.mar` → `testmar`), so all qualified symbol paths are `stem::module::name` — never the filesystem path, never bare `name`. The generated entry function must claim the LLVM symbol `main` before any user function is emitted: the Mach-O linker binds the process entry to bare `main`, so a user function taking that name (possible for degenerate entry paths with no stem) becomes the entry and its garbage return register becomes the exit code.

Read `CONTRIBUTING.md` for the commit message format before committing.
Trait method signatures retain their own generic declarations in `FunctionTy`; trait dispatch combines receiver-implementation generics with method generics before converting method arguments and returns.
User-defined, extern, and synthesized closure `FunctionTy` values retain the generic declarations carried by their symbols; do not construct them with the generic-free constructor.
Function-type and closure AST arguments preserve their `&` inout marker through semantic conversion; closure lowering uses pointer parameters with local writeback, and function-type equality and trait method signature validation compare that marker.
Numeric tuple accessors lex as separate `Dot` and integer tokens, including chains such as `value.0.1`; decimal literals remain digit-started.
Trait declarations accept generic type parameters (e.g. `trait Trait<T>`); trait implementation entries store the namespace, trait and receiver generics, implementation generics, declaration, and optional bound diagnostic so multiple implementations can coexist across different trait generic arguments. Trait bounds in `BoundedGeneric` store full generic references (`Generic<'me>`) checked via `type_implements_trait_generic`.
Trait generic-argument bounds are validated at concrete impl and generic-bound declarations; method lookup propagates the recorded `TypeDoesntImplTrait` diagnostic and must not fall back to a misleading missing-field error.
